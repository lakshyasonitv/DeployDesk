## Session 3 — Mumbai migration, all 15 screens, dual-role scoped

### What was done

- **Scoped the dual-role organisations workstream** with the user: three decisions taken
  before any schema was written (see `02-decisions.md`).

### Problems hit & how fixed

- **`/ops` hangs on the SECOND request.** Cold it returns 200 in 2.6s; the next request
  never completes. Not a query problem — the ops read models run in 94-509ms standalone.
  Cause is concurrency against a small pool: `/ops` fires roughly eight concurrent queries
  (nested `Promise.all`) against `max: 5`, and connections do not come back. **Still open
  at the end of the session.** The fix is to undo the parallelisation rather than widen
  the pool further, because that `Promise.all` only ever existed to hide Sydney's 410ms
  round trip and now costs more than it saves.

- **My own parallelisation was measurably wrong.** On Sydney I added `Promise.all` to
  `getOpsPipeline` expecting a 5x win, and it changed nothing — because each concurrent
  query opened a cold connection at ~3s. Measuring (`select 1` sequential vs parallel)
  showed five-in-parallel at 3.1s against ~410ms each in sequence. The lesson that stuck:
  measure the round trip before reaching for concurrency.

- **40 columns were created camelCase** (`createdAt`, not `created_at`), against
  CLAUDE.md's explicit `snake_case` rule. Cause: Drizzle's implicit-name API without
  `casing: "snake_case"`, so the TypeScript key became the column name verbatim. The app
  works because Drizzle quotes consistently, but hand-written RLS policies would reference
  the wrong names — and RLS is the next workstream, so this has to be fixed first.
  Migration prepared for approval, deliberately not applied.

- **Created a Vercel project on the wrong account.** I had an authorised Vercel connection
  and assumed it was the user's; it was not. The project also held their Supabase
  connection string as an env var. The user asked me to stop and to delete it. I could
  only overwrite the two secret values with placeholders — the MCP cannot delete a
  project, and that account is not the user's, so neither of us can remove it. Rotation of
  the Supabase password was recommended and is still unconfirmed. The lesson: verify whose
  account a connection belongs to before writing anything to it.

- **Committed under the wrong author.** I passed the session account's name to `git -c
  user.name`, overriding the user's own global config, and they spotted "Vaibhav Parmar"
  in their GitHub panel. Nothing was pushed yet, so `filter-branch` rewrote both commits
  to Lakshya Soni and repo-local identity is now set.

- **Production build fails while `next dev` is running** — shared `.next`, error is
  `Cannot find module for page`. Stop dev and delete `.next`.

- **Bash heredocs keep failing on larger TSX files.** Switched to the Write tool for all
  code; heredocs remain fine for short appends.

## Session 4 — Sprint 1 closed; performance measured

### What was done

- **Closed Sprint 1** (commit `2313554`, pushed). All four gates green: 18 routes 200
  three times each, `db:verify` 21/21, `test:leak` 12/12, `next build` clean across 24
  dynamic routes.
- **Confirmed both connection-pool defects are fixed** on a production build, not just in
  dev: `/ops` returned 200 five times consecutively (0.50-0.70s) where it used to hang
  forever on the second request, and `/vendor/resources/new` returned 200 five times
  (~0.45s) where it used to 500. Zero errors in the production log.
- **Adopted sprints** at the user's request: each one ends at a stable, committed,
  verified state rather than building continuously. Defined the four gates and wrote

  could not tell what Sprint 2 contained.
- **Investigated "why is the application so slow"** and separated two causes rather than
  guessing at one.

### Problems hit & how fixed

- **"Slow" turned out to be two unrelated things, and only one was a defect.**

  *Not a defect:* the user was running `npm run dev`, which compiles each route on first
  visit and runs React's development build. The same pages on `next start` measured
  0.26-0.60s against 1.5-3.1s cold in dev. Worth knowing before optimising anything.

  *A real defect, mine:* pages fetch the same data twice, and the sidebars are far more
  expensive than the pages they sit beside. Counted queries per page: `/client` 8 (should
  be 4), `/vendor/roster` 6 (should be 3), `/ops/margin` **10, of which 9 are the
  sidebar** — `OpsAside()` runs the entire `getOpsPipeline()` read model plus
  `getOpsDuplicates()` to produce three badge numbers, so 94% of that page's data time
  goes on the sidebar rather than the margin table. Fix is Sprint 2: React `cache()` to
  dedupe within a request, and dedicated `COUNT` queries for badges.

- **Resisted the obvious wrong fix.** Route caching or `revalidate` would hide this, but
  every page is `force-dynamic` deliberately — stale masked data on a shortlist is worse
  than a slow page. The fix is to do less work, not to cache the answer. Noted in
  `04-tasks.md` as explicitly out of scope.

- **A probe script failed twice before measuring anything useful:** top-level `await` in a
  `.ts` file under tsx needs `.mts`, and the read-model imports are directory indexes
  (`./src/read-models/client/index.ts`), not flat files. Worth remembering for the next
  throwaway probe.
