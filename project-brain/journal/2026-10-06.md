## Session 5 — Sprint 2: performance

### What was done

- Gave each portal's sidebar its own `COUNT` query (`getClientSidebar`,
  `getVendorSidebar`, `getOpsSidebar`) instead of calling a full read model for badge

  pre-sprint commit serves on :3100, the new build on :3000, sharing `node_modules` via a
  junction.
- Measured both query counts and wall-clock, six samples each.

### Results

Queries per page: `/ops/margin` **10 → 2** (471ms → 60ms of data time),
`/ops/duplicates` → 4, `/client` 8 → 6, `/vendor/roster` 6 → 4.

Wall-clock, six-sample means, BEFORE vs AFTER:

| Route | Before | After | Change |
|---|---|---|---|
| `/ops/margin` | 0.589s | 0.120s | **+80%** |
| `/ops/duplicates` | 0.547s | 0.235s | **+57%** |
| `/ops` | 0.579s | 0.444s | **+23%** |
| `/client` | 0.349s | 0.365s | −5% (noise) |
| `/vendor/roster` | 0.271s | 0.261s | +4% (noise) |

### Problems hit & how fixed

- **The React `cache()` plan was dropped, and that was the right call.** First attempt
  rewrote `export async function X(` into `export const X = cache(async function XImpl(`
  by regex, which left the closing `}` without its `)` — a syntax error across five
  functions, reverted with `git checkout`. Then the better realisation: once the sidebars
  stopped calling the heavy read models, **no page called the same read model twice**, so
  there was nothing left to dedupe. The structural fix made the memoisation unnecessary.

- **Two pages did not get faster, and I reported that rather than hiding it.** `/client`
  and `/vendor/roster` moved −5% and +4% over six samples — inside noise — despite real
  query reductions. Their latency was never dominated by the sidebar. The lesson: a query
  count is not a latency measurement.

- **`db:verify` dropped to 20/21 mid-sprint and it was NOT a regression.** The failing
  check was "exactly one SLA breach", now finding REQ-2295 *and* REQ-2302. REQ-2302 is
  stage `new`, documented window 4 business hours, and the fixture wants it `warn` — which
  means 25% or less remaining, so its deadline sits under an hour out and ages into `late`
  as real time passes. Re-seeding (3.5s) restored 21/21. Diagnosed before touching
  anything, which avoided hunting a phantom bug in the sprint's own changes.

  Underneath it is another fixture/spec conflict like ADR-011: the fixture's own label for
  that row is "SLA 12h = warn", which implies a window near 48h, not 4h. The durable fix
  is a per-requirement SLA window column, proposed for the Sprint 3 migration batch.
