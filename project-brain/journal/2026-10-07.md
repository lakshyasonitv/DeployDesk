### Problems hit & how fixed

**The brain's own note about `getVendorRoster` was wrong, and following it would have
wasted the sprint.** The note read: *"moves 173 rows to render 9 … needs server-side
paging, which also means moving the roster's filter pills from client-side to
server-driven."* Both halves were aimed at the wrong call site.

- The roster **page** renders all 42 cards, so 173 rows is proportionate there. There is
  nothing to page and the filter pills can stay client-side.
- The waste was `getVendorOverview` — the vendor **dashboard** — loading the same 173 rows
  and shaping 42 view objects in order to display **six integers**.

Fixed in two measured steps:

1. A shared `getVendorRosterCounts()` aggregate replaced the roster load in both the
   dashboard and the sidebar. **481ms → 437ms, only 9%.** The rows were never the problem.
2. The five independent reads in `getVendorOverview` now run in one `Promise.all`.
   **437ms → 144ms.**

**The real lesson, which contradicts how the note framed it: latency here is round-trip
count, not row count.** Six sequential queries to Mumbai at ~60–70ms each spent almost all
their wall time waiting. Look for serial `await`s before optimising row volume.

**A trap avoided: the two "assessments pending" figures had silently diverged.** The
sidebar counted assessment ROWS not scored; the dashboard counted RESOURCES with no scored
assessment. Both printed `13` on the current data, so no test and no eyeball would have
caught it — but they diverge the moment someone retakes a test (a pending attempt 2 against
a scored attempt 1). Rather than "aligning" them as a separate act, both call sites now go
through one function, so the second definition no longer exists to drift from. The
resource-based definition was kept because it is what the label means: *13 people still
waiting on a result*.

**Reintroducing `Promise.all` looked like re-breaking a fixed bug, and is not.** Sprint 1
records that removing a fan-out cured the `/ops` hang, so a future session will reasonably
flinch at this. The actual root cause then was the pool at `max: 1`, deadlocking against
Supavisor's transaction mode. The pool has been `max: 10` since Sprint 2, and a two-way
`Promise.all` already ships on ten pages. A five-way fan-out is well inside the pool.
**Verified**: all 17 routes 200 against the production build, `/vendor` 0.27s.

**How the "no behaviour change" claim was actually proven.** The existing four gates cannot
catch a displayed number silently moving from 7 to 8 — routes still return 200 and the
tests do not assert dashboard values. So all six rendered figures were captured **before**
the change (stats 30/42/3/79% + ₹8.84L, freshness 35/4/3, alerts 4/3/13, badges 42/13) and
asserted byte-identical **after**. Worth repeating for any read-model refactor.

**A threshold check done before trusting the SQL.** Moving freshness into SQL only works if
it agrees with the JS `freshnessFor()` helper. Confirmed on both boundaries and on a null
`last_confirmed_at`: `floor(x) >= 10` iff `x >= 10`, so the `>= interval '10 days'` /
`< interval '14 days'` predicates match the helper exactly. The duplication is deliberate
and commented, not accidental.

### Problems hit & how fixed

**The shell could not be migrated by script, and finding that out first saved the sprint.**
v1's sidebar was dark `#111114` with `#fff` text. `#fff` maps to `--surface`, and v2's
sidebar *is* `--surface` — so the obvious blanket substitution yields white text on a white
sidebar. Shell and Skeleton were therefore rewritten by hand. `Skeleton.tsx` had in fact
already been broken this way by the script (`color:var(--surface)` on the wordmark) before
being rewritten, which is the proof the concern was real rather than theoretical.

**`color:#fff` has two correct answers and the script can only pick one.**

- on a `--t1` or status background it must become `--surface`, so it inverts in dark mode
  (v2's "Dark button" recipe is literally "`--t1` background, `--surface` text")
- on a `--brand` background v2 says white **stays literal white**

The script turned all 22 into `--surface`; three were on brand backgrounds and were restored
by hand (`PostForm` x1, `ShortlistBoard` x2). Found by grepping for brand-background and
surface-text adjacency, not by eye.

**An automated check found the class of bug that review misses.** A scan for declarations
whose `color` and `background` resolve to the *same* token catches invisible text directly.
It reports 0. Re-run it after any further colour work — it is the cheap guard.

**The advisor was right to block an earlier framing.** The draft plan claimed the foundation
could be done "additively" by repointing `TOKENS` under the `s()` helper. Measuring first
showed 151 token references against 885 bare hex literals, so that would have re-themed
about 15% and shipped a visibly half-themed app. The option costs put to the user were
corrected before they chose.

**THE BIG ONE: the portal guard made the entire feature unreachable, silently.**

| portal | requires |
|---|---|
| `client` | `can_hire` |

### The bug: next/link cannot navigate to a Route Handler

The organisation names in the top bar did nothing when clicked. They used `next/link`, but
`/demo/act-as` is a **Route Handler**, not a page — it answers with a 307 and a
`Set-Cookie`. `next/link` performs a client-side RSC navigation: it fetches the destination
expecting a flight payload, gets a redirect to HTML, and the transition silently does
nothing.

Worse, **`next/link` prefetches by default**, so merely rendering the top bar could have
issued a GET to the handler and set the cookie with no click at all.

A plain `<a>` does a full browser navigation, which follows the redirect and honours
`Set-Cookie`. **Rule: `next/link` for pages, `<a>` for route handlers.** The workspace tabs
keep `next/link` because `/client` and `/vendor` are real pages.

### Audit findings

**A business rule written three times, one copy dead.** The self-dealing rule existed as
the SQL functions (used), `mayBeOfferedTo()` in TypeScript (dead), and a hand-copied inline
version in the match-preview route. match-preview now calls `mayBeOfferedTo()` — it cannot
use `is_self_dealing(resource, requirement)` because **at preview time there is no
requirement yet**, which is exactly what the org-level helper is for. Verified identical:
pool 91 for a client-only org, 78 for the dual-role org, the same 13 exclusions.

**`pct < MARGIN_FLOOR_PCT` inlined six times across four files** while `isBelowFloor()` sat
unused. And the margin/SLA state ramp re-tested `marginBand()`'s own thresholds in different
vocabulary. Both now go through the helper, so 25/18 exists once.

**A stale comment was holding the slowest page slow.** `/ops/matching` was ~1.0s and carried
*"Sequential: OpsAside alone issues several queries, and running it alongside others
exhausted the connection pool."* Both halves had become false — Sprint 2 reduced `OpsAside`
to one count query, and the pool went 5 → `max: 10`. Five reads now run together:
**1.035s → 0.489s**. The same stale comment was repeated on `/vendor/resources/new`:
**0.491s → 0.334s**. `getClientOverview` went **340ms → 132ms** (six serial reads → two
waves), output byte-identical.

**The lesson worth keeping: a comment explaining why something must stay slow needs
re-checking when its reason is fixed.** This one cost 2× on the worst page in the app.

**A documented rule that was never implemented.** `organizations.fee_model` has always
carried a comment saying dual-role orgs default to a flat declared fee — and nothing set it,
so every organisation including Cygnet sat on the column's `hidden_markup` default. That is
the **commercial half of the masking rule**: a company on both sides can compare what it is
paid as a supplier against what it is charged as a client and read the spread off the
difference. The seed now sets it, `db:verify` asserts it, and the column uses its enum
instead of plain `text`.

**Dead code: 9 unreferenced exports → 2, and 20 unused imports/locals → 0.**
`noUnusedLocals` and `noUnusedParameters` are now on, which is what stops them returning.
Removed `ownBenchPredicate` (superseded by the `ops_v_own_bench_matches` view),
`opsSuffixedId`, `parseReliability`, `POOL_OF`, the `NavItem` interface.

The two kept deliberately both flag something real, and should not be "tidied away":
- **`rate_changes`** is declared and never written because no rate-change path is built yet.
- **`IST_TZ`** is unused because **nothing converts to Asia/Kolkata**. `CLAUDE.md` working
  agreement 3 says business clocks run there, so SLA and freshness are currently computed in

**The masking contract had to be read, not assumed, and it contradicted itself once.**
`02-decisions.md:203` records "rate bands everywhere on the client side, placements
included", while the live screen shows an exact figure via `formatPaiseShort`. Resolved by
the legend plus the suite rather than by picking one: `🔸` means *own records only*, the band
rule (`🎭`) is specifically for **masked shortlist cards** pre-placement, and
`tests/leak/read-models.test.ts:89` already asserts "a client's own budget band and the
client rate on its own engagements are visible". So the exact rate is correct and the panel
**introduces no new money field** — it reuses `rateLabel`. A pre-existing discrepancy in the
decision note was left alone rather than silently resolved inside a feature.

**Tenancy on this path needs two predicates, not one.** `shortlist_items` has no client
column; it reaches a client only through `shortlists → requirements.client_org_id`. The
snapshot query therefore pins **both** the engagement's `client_org_id` and the
requirement's. With only the first, a resource placed at two clients matches the other
client's shortlist row and we serve its snapshot. There is now a test that fails if the sets
overlap.

**A leak test that passed vacuously.** The `with_supplier` assertion originally swept two
hard-coded clients, but the seed attaches its single extension request to whichever active
engagement the database returns first — **unordered**, so which client owns it is not fixed.
The test would have passed by finding nothing. It now sweeps every client org and asserts
`labels.length > 0` first, so it fails if the fixture ever stops producing one. A vacuous
leak test is worse than no leak test.

**A wrong first attempt at the header button, caught while writing it.** The header's
"Request an extension" has no person attached, so the first version bound a DOM listener to
it from the island via `useMemo` — which is not for side effects and would not have fired
reliably. Deleted rather than converted to `useEffect`: an extension belongs to one person,
and a header button cannot say which of five placements is meant. The control lives on the
person, which is a deliberate departure from `SCREENS.md:96`.

**THE 9999px CARD.** Reported as *"the candidate are like that like they can expanded
horizontally so it is not making any sense and also it is not working properly"*. One cause,
both symptoms:

```
<ScoreBars sections={c.sections} width={9999} />   ->  width: 9999px
```

`ScoreBars` only accepted a number, so **"fill the container" was unrepresentable** and a
sentinel stood in for it. The cards sit in a `repeat(3, 1fr)` grid, and **`1fr` is
`minmax(auto, 1fr)`** — so each column's *minimum* became its child's min-content width. The
cards stretched far past the viewport and carried their own buttons off screen, which is why
the screen also looked like it was not working. The shortlist itself was fine: it has always
persisted through `/api/client/shortlists/decide`.

Fixed by making the intent sayable (`width?: number | string`) rather than by clamping the
number, which would have hidden the API gap that caused it. `maxWidth: 100%` and
`minWidth: 0` were added too, so the bars can never dictate their container again. The grid
was also `repeat(3, 1fr)` at **every** width, squashing on a narrow window; now
`repeat(auto-fit, minmax(272px, 1fr))`.

**`tests/layout-guards.test.ts` is a lint, and it was proven rather than asserted.** Same
reasoning as `client-boundary.test.ts`: this type-checked, built clean, server-rendered
correct HTML and passed all 108 tests — it was visible only to a person looking at the page.
The guard fails any inline pixel width over 2000px. **Verified by reintroducing
`width={9999}` and watching it fail** with the right file, line and reason, then restoring.

**One string the vocabulary pass missed.** `getClientInterviews` produced *"Broker is
confirming supplier release"* — found while reading the leak suite, which asserts it
verbatim. The earlier sweep grepped for the phrases `your broker` / `Your broker` /
`Talentvibes broker` and this matched none. Now *"Your Talentvibes team is confirming
availability"*, matching the shape used for extension requests. **Grep for the word, then
filter — phrase-greps miss the sentence you did not think of.**

**Two bugs caught on review, after the feature already worked.**

*The date picker and the endpoint disagreed about what a day is.* The island built the
`min` and default with `new Date(`${endDateIso}T00:00:00`)` — **local** midnight — while
the route parses `T00:00:00Z`. In any timezone BEHIND UTC the picker would therefore offer
the earliest date and the server would answer `date_in_past`. Fixed on one side, not both:
the island now does all its arithmetic in UTC (`afterBoth()`), so the two ends agree by
construction.

*State carried between people.* `{open ? <PlacementPanel .../> : null}` reconciles by
element position, so opening person A then person B could keep A's `until`, `note` and form
state — including A's end date as B's default. One attribute: `key={open.maskedId}`.

**A verification that was itself vacuous, which is the lesson worth keeping.** The timezone
fix was first "proved" by running a check under `TZ=America/Los_Angeles`,
`TZ=Pacific/Kiritimati` and so on, and all four printed identical, passing output. They
printed identical output because **Node on Windows ignores named zones** — every one of them
resolved to offset 330, and only `TZ=UTC` actually differed. The run had tested one timezone
four times and been read as four.

Redone as arithmetic instead, modelling "local" as UTC+offset independently of the runtime
clock, which is what Date's local getters do anyway. That showed the real shape: the old code
is rejected for **8 of 24 hours at UTC-8 and 11 of 24 at UTC-11**, scaling with distance
behind UTC, and never at UTC, IST or UTC+14. So the bug was **latent for this product** —
its users are in India — but live for anyone travelling. The new code: 0 of 24 at every
offset tested.

*If a check passes identically across every variant, suspect the harness before believing
the result.*
