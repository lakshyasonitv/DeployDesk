### Problems hit & how fixed

**An 11:00 interview was showing as 05:30 on the deployed site.** `IST_TZ` was declared in
`src/lib/derived.ts` and used for **documentation only**. Sixteen formatters passed
`"en-IN"` with no `timeZone`, which formats in whatever zone the process runs in — UTC on
Vercel. Proven rather than argued:

```
OLD (no timeZone): 05:30
NEW (pinned IST):  11:00
```

Working agreement 3 puts business clocks in Asia/Kolkata and says convert at the edges. The
earlier audit that introduced the business clock fixed the **arithmetic** and left the
**rendering**, so the rule had been half-applied for the product's whole life. One helper,
`istFormat(value, opts)`, taking the Intl options each site already passed. Money formatters
untouched: `toLocaleString("en-IN")` on a *number* has no timezone to get wrong.

**A filter that disagreed with the thing it filters — caught by making the check exact.** The
three freshness states are exhaustive and mutually exclusive, so their counts MUST sum to the
unfiltered total. They summed to one more. The `unconfirmed` condition was an
un-parenthesised OR, so `and(...conds)` produced

```
status in (...) and last_confirmed_at is null or days >= 14
```

which SQL reads as `(status in (...) and last_confirmed_at is null) or (days >= 14)` — the
second branch escaping the status filter and pulling in withdrawn profiles. **An OR inside an
AND needs its own parentheses, every time.** Verified by removing them again and watching the
test fail with "expected 119 to be 118".

The same pass also found that the freshness filter had to use **IST calendar-date
subtraction**, not `now() - interval '10 days'`: elapsed-hours arithmetic would let a row sit
under "Needs confirming" while its own pill read "Confirmed". Zero disagreements across all
three buckets now.

**`search` was worse than inert.** It filtered in memory **after** `.limit(60)`, so it looked
at the first 60 rows of 1,284 and the count beside it described the page. Pushed into SQL with
the rest, and `matchCount` is now counted in the database with no limit, separate from
`resultCount`.

**The score filter had to be pinned to the latest attempt.** Otherwise someone whose first
attempt scored 90 and whose retake scored 60 passes an "80+" filter and then renders 60.

**A control that needed a table it does not have.** "Panel availability" was going to become a
read-only list of slots behind the existing button. That was the wrong answer and it was
caught before building: it renames a **write** control into a **view**, so a person clicks
"set" and gets a list. Recurring availability has nowhere to live —
`interview_slots.interview_id` is `not null`, so every slot hangs off one round — which makes
it a new table and therefore the owner's call under the database-safety rule. **Removed from
the screen** and recorded, rather than faked.

**The slot Undo could have been a privilege escalation.** The first sketch had the client send
back the status to restore. A client-supplied "put it back to confirmed" is a one-line way to
mark an unbooked interview as booked. The status is now **derived**: a standing booking plus
an accepted slot means `confirmed`, any slot still pending means `awaiting_vendor`, otherwise
`proposed`.

**The slot picker means IST wherever the browser is.** A `datetime-local` input returns the
*viewer's* wall clock, and the validation window is IST — so a viewer outside India picking
11:00 would be offering 05:30 IST and be told it was outside business hours. Correct, and
baffling. Same class as the extension-date bug from yesterday, and this time it was designed
out rather than found.

**Two columns on `interview_slots` are deliberately not read.** `proposed_by_user_id`
identifies a person, and on a vendor-proposed slot that person works for the supplier.
`decline_reason` is free text and the table has **no `declined_by`**, so there is no way to
know whether a broker or the supplier wrote any given reason — and *that ambiguity, not the
wording, is what makes it unsafe*. Same rule as `interview_feedback.notes` waiting for a
broker-authored `relayed_summary`; no such relay column exists for slots, so the client is
told a time did not work and not why.

**A test run hung for ten minutes and it was not the code.** `npm test` stopped producing
output; the node processes sat at near-zero CPU, which is I/O wait, not a loop. Running a
single suite immediately afterwards passed in 7s — the pool had been briefly exhausted by
four vitest runs in quick succession. Stopped the task rather than killing processes, and
re-ran. Worth remembering before debugging a "hang" that is really a connection queue.

## Session 2 — the landing page becomes a redirect

### What was done

`/` was a deployment smoke page: eight table counts, a live masked-shortlist read and three
portal links. The owner's point was simple — the organisation switcher is in the top bar now,
so the links are redundant. It is a redirect: the acting-org cookie through `landingFor()`,
defaulting to `/client`.

### Problems hit & how fixed

**Removing it made two things dead, and dead code is the thing to notice.**
`getPortalSwitcherOptions()` had exactly one caller — that page — and its `title()` helper had
exactly one caller in turn. Both deleted. Same reasoning as the `ROLE_LABEL` map: a function
that still exists implies a caller.

**The landing rule was about to be duplicated.** `getShellNav` already had
`r.isOps ? "/ops" : r.canHire && !r.canSupply ? "/client" : "/vendor"` inline, and `/` needed
the same thing. Extracted as `landingFor()` so there is one definition — and then discovered
the switcher's hrefs had **never been asserted by any test**, so changing that expression
would have silently moved where the root URL sends people. Four tests on it now.

**Verified by request, not by build.** The lesson from the search crash is that a page can
type-check, build clean and still be wrong, so: `next start` on a spare port and
`curl -D -` against `/`, which answered `307 Temporary Redirect` with `location: /client`. A second check with a cookie was
inconclusive because the ad-hoc org-id lookup came back empty — rather than keep hacking at
it, the cookie branch is covered by the `landingFor` tests, which is where the logic actually
lives.

**One thing deliberately left.** `ACCENT_GRADIENT` in `style.ts` is now unused. Kept, because
it is a design token from the v2 handoff rather than logic — an unused palette entry is a
palette; an unused function implies a caller.

## Session 3 — a draft was a one-way door

### What was done

Reported from the screen: a person added and saved as a draft could not be found in the ops
talent pool, was not on the skill tests page, and there was no way to add him.

**Every one of those observations was correct, and they had three different causes.** Fixed
all three, plus the "Invite to test" button that had never had a handler. 141 tests (was
135), build and typecheck clean.

### Problems hit & how fixed

**Diagnosed from the code before touching any data**, which explained all of it and avoided
an ad-hoc query against the owner's database:

1. **The ops pool excludes `draft` — and that is correct.** A draft is not an offer. Nothing
   on screen said so.
2. **The roster rendered each row's ASSESSMENT status and never its RESOURCE status**, had no
   drafts tab and no draft count. A draft was pixel-identical to a listed profile.
3. **No endpoint anywhere moved `draft` to `listed`.** The add form could create a state that
   nothing in the product could undo.

The owner confirmed "Save as draft", which ruled out a fourth bug — had it been "Add to your
bench" the person would have been row 1 of the pool, which sorts by `last_confirmed_at`
descending and listing stamps it with `now`.

**The skill tests screen asked its question the wrong way round.** `getVendorAssessments`
read `FROM assessments INNER JOIN bench_resources`, so it listed only people who **already
had a test record** — and someone just added has none. They were structurally invisible on
the one screen whose job is to get them tested. And `summary.notStarted` counted *assessment
rows* at status `not_started` rather than people with no test, so the header read **"Invite 0
to test"** on a bench full of untested people. It reads from the bench now, which is the
direction the question is actually asked in.

**A retake would have duplicated a person.** A left join yields one row per `assessments`
row, and a second attempt is a second row. Deduped on highest `attempt_no` — the same rule
the pool's score filter uses.

**"Request a test" needed a decision, not wiring.** ADR-006 puts the provider behind an
adapter that does not exist. Three options went to the owner; the chosen one records the
request at status `invited` with `provider_ref` null, and the copy says "test requested",
never "invitation sent", because nothing has been sent. **Faking a score was the option to
refuse on its own merits:** an independently proctored result neither side can influence is
the entire product, and a number written by our own endpoint would be indistinguishable in
the database from a real one later. A test asserts `provider_ref` and `overall_score` stay
null.

Two labels would have become lies and changed with it: the status pill said **"INVITE SENT"**
and the empty-score caption said **"INVITE NOT SENT"**.

**Idempotency mattered because of what the button is** — it acts on *everyone* untested, so
pressing it twice must not queue anybody twice. Already-open requests are skipped and
reported, not rejected. The Undo sets rows to `abandoned` rather than deleting them.

**The regression test walks the whole path rather than asserting each piece**, and that shape
is deliberate: **each of the three original defects was defensible alone.** The bug was that
together they left no way forward — a fault no single-screen review finds.

**`db:verify` is 28/2 and it is not this work.** Both failures are the SLA decay, and the
failure message says so itself. Fourth occurrence, fourth time it cost nothing.

**A mistake of my own worth recording.** The brain-update script used a non-idempotent
`append()`, and running it twice duplicated three sections. Caught by grepping the section
headings for counts, fixed by `git checkout -- project-brain/` (none of it was committed) and
re-running once. **A script that edits files in place needs to be safe to run twice**, because
sooner or later it will be.
