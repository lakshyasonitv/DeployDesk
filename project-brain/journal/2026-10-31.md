Status only. Nothing fixed yet; the owner's pattern is status, then questions, then fixes.
Tested in the browser, checking the database before and after each click, and restored

### Works

- **Keep A / Keep B / Two different people** call `POST /api/ops/duplicates/resolve`, which
  writes the flag, withdraws the losing submission and writes an audit row in one

  these as dead buttons, but `ResolveActions.tsx` wired them.
- Sidebar badge and "Today's queue" count only `open` flags, so they update correctly.

### Defects, verified

1. **A settled flag never leaves the page.** `getOpsDuplicates` has no status filter and the
   page groups by `blocks = confidence >= 85`, ignoring status. After "Keep Nimbus" and a
   reload, DUP-0148 still read "Likely the same person · blocks 1 shortlist" with all three
   buttons live. The matcher and shortlist-send both treat only `open` and `>= 85` as
   blocking, so this page is the odd one out.
2. **Clicking again withdraws BOTH people.** The route has no guard on the current status.
   "Keep Nimbus", then "Keep Orbit" on the same card left TV-4821 AND TV-7188-B
   `withdrawn`, so the person was off the exchange entirely. Verified in the database.
3. **The 60–84% flags have no controls at all.** DUP-0147 says "Needs a human call" with no
   way to make one.
4. **The recommendation weighs reliability only** (A wins ties), while the copy and
   `docs/DOMAIN.md` say it weighs which submission came first, freshness AND reliability.
   "SUBMISSION A · EARLIER" is decided by position, never compared: in the seed, both were
   submitted at the same minute, and the flag is dated three days before either.
5. **"N open flags"** is a primary-styled button that does nothing. **"Detection rules"** is
   inert, as already known.
6. **Undo relists to `listed` regardless of previous status**, so a side that was already
   withdrawn for another reason comes back. The route's own comment accepts this; worth a
   decision.
7. **DOMAIN says `→ shortlisted` is blocked by an open flag listing that requirement**, but
   `app/api/ops/requirements/stage/route.ts` does not check it. Only the shortlist-send
   path does, and it checks by resource, not by `blocks_requirements`.
8. The copy says "Notify the other supplier", but nothing notifies anyone. The broker-thread

## Session 6 — Duplicate checks: a flag is settled once

### What was done

Fixed findings **1 and 2** from Session 4, on the owner's "Yes, fix it".

- **`POST /api/ops/duplicates/resolve`:** the flag UPDATE is now conditional. Settling
  requires `status = 'open'`; re-opening (Undo) requires `status <> 'open'`. If no row
  matches, the call returns **409** (`already_settled` / `already_open`) and withdraws or
  relists nobody. The condition is on the write rather than on a read beforehand, so two
  brokers clicking at once cannot both pass it.
- **`getOpsDuplicates`:** `blocks` is now `confidence >= 85 && status === 'open'`, the same
  rule the matcher and shortlist-send already used. A settled flag drops to the compact list
  as "Settled: kept Nimbus Softworks." with a green dot and no buttons, and comes back as a
  full card with buttons if it is re-opened.
- **New test** `a duplicate flag is settled once` (`tests/leak/write-paths.test.ts`). It
  **failed against the old route** ("expected 200 to be 409") and passes with the fix. It
  restores the seed in a `finally` and deletes only its own audit rows.
- Verified in the browser and over HTTP: settle, then reload (the row shows as settled),
  then a stale second settle (409, nobody withdrawn), then re-open (200, both listed), then
  re-open again (409). The data ends at the seed baseline.

### Decided without asking, and why

Settled flags stay VISIBLE (compact, labelled) rather than disappearing. That is the
smaller change, it hides nothing, and it is reversible either way. Whether they should
instead move to a separate "Settled" section is still the owner's call.
